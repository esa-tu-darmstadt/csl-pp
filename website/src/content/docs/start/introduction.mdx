csl++ is an open-source language frontend for the Cerebras Software Language. It is a place to develop language features that CSL does not have: a feature is implemented as a transformation in the compiler `csl-pp`, which translates a csl++ program to vanilla CSL and then compiles the result with `cslc`, the compiler of the Cerebras SDK.

Two extensions are part of csl++ today, async CSL and automatic resource allocation. This page explains the problems in CSL that they address. The [Tutorial](../../tutorial/) shows them on a complete program.

## Control flow in CSL

A CSL program is a set of tasks. An asynchronous DSD operation, such as a transfer to or from the fabric, runs in the background and activates a task when it completes. A task runs to completion, so a computation with several such operations is written as several tasks, or as one task that is activated after each operation and keeps its position in a state variable:

```csl
var state: u16 = 0;

task step() void {
  switch (state) {
    0 => { @fmovs(out_dsd, x_dsd, .{ .async = true, .activate = step_id }); state = 1; },
    1 => { @fadds(x_dsd, x_dsd, in_dsd, .{ .async = true, .activate = step_id }); state = 2; },
    else => { done(); }
  }
}
```

Every value that lives from one step to the next is a global variable, a loop over the steps is a counter that the state machine checks, and a library that performs such a sequence takes a task ID as a parameter to report its completion.

In csl++, a task can suspend. An `async task` ends its current run at `suspend` and continues after it when the task is activated the next time, with its local variables intact:

```csl
async task step() void {
  @fmovs(out_dsd, x_dsd, .{ .async = true, .activate = @current_task() });
  suspend;
  @fadds(x_dsd, x_dsd, in_dsd, .{ .async = true, .activate = @current_task() });
  suspend;
  done();
}
```

An `async fn` packages such steps as a function that is called with `@await`, and `@await_parallel` runs several calls at the same time. A library offers async functions instead of taking task IDs. See [Async functions and tasks](../../language/async/).

## Resources in CSL

A CSL program names its colors, task IDs and queues by number. The numbers of all modules must be distinct, so the programmer keeps a table of them, usually as a comment in the layout file, and passes them into every library:

```csl
// color map: memcpy uses 20-23, allreduce 8, stencil 0-7, ...
const reduce = @import_module("allreduce/layout.csl", .{ .C_ROUTE = @get_color(8) });
```

In csl++, a module claims what it needs. A claim at compile time returns a resource that no other claim and no fixed ID of the program uses; a claim at runtime takes one from those that are left:

```csl
const C_ROUTE: color = @claim_color();
const iq: input_queue = @claim_input_queue();
```

A library claims its own resources, so the importer passes none, and two libraries, or two instances of the same library, never collide. See [Claims](../../language/resources/).

## The compiler

`csl-pp` parses a csl++ program, evaluates its comptime code, and transforms it in its own intermediate representation. Then it writes vanilla CSL and runs `cslc` on it. A compiler with its own IR could hand its result to a backend directly; Cerebras keeps the backend of `cslc` closed, so `csl-pp` uses the only input `cslc` accepts.

<Pipeline />

`csl-pp` accepts the command-line arguments of `cslc` and can replace it in build scripts. Host programs, memcpy and the simulator are unchanged. The generated CSL is readable, with one file per distinct PE program. The same frontend serves the [VS Code extension](../../tools/vscode/), which checks a program while it is edited.
